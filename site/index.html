系統概述
SYSTEM OVERVIEW

本次作業以 OpenCV 為核心實作人臉辨識系統，分成兩大部分：

  • 人臉辨識引擎 — HAAR Cascade 負責人臉偵測，LBPH 負責辨識是誰
  • Web 遙控介面 — Flask + HTML/CSS/JS，把影像串流、方向鍵遙控、線上註冊整合成一個網頁

技術選型理由

為什麼選 HAAR + LBPH 這個組合：

技術用途選擇原因
HAAR Cascade 偵測畫面中哪裡有臉 純 CPU 即可即時執行（實測 30 FPS），不需要 GPU 或額外模型檔，符合樹莓派效能限制
LBPH 判斷這張臉是誰 訓練只要幾秒鐘（實測 0.1 秒）、模型檔僅 2.8 MB、對光線變化有一定容忍度，非常適合邊緣裝置
直方圖均衡化 + CLAHE 影像正規化 消除明暗差異，讓同一個人在逆光、偏暗環境下仍能辨識
Flask Web 後端 課程指定，且輕量、部署簡單
設計主軸 為了能「先在電腦測試，成功後直接搬上車」，整個系統把硬體相依的部分集中在兩個檔案： camera_source.py（鏡頭來源）與 motor_control.py（馬達控制）。 上層程式只呼叫 cam.read() 和 motor.move("forward")， 底層是電腦的 Webcam 還是車上的 Picamera2 完全無感。

執行流程

整套系統的資料流分成「背景擷取」與「HTTP 回應」兩條線，避免互相阻塞：

  ┌──────────────────── 背景擷取執行緒 ────────────────────┐
  │                                                          │
  │  攝影機擷取 (640×480)                                     │
  │      ↓                                                   │
  │  鏡像翻轉 cv2.flip                                       │
  │      ↓                                                   │
  │  轉灰階 cvtColor(BGR2GRAY)                               │
  │      ↓                                                   │
  │  HAAR Cascade 偵測人臉                                   │
  │      ↓                                                   │
  │  裁切人臉 crop_face（往外擴 25%）                        │
  │      ↓                                                   │
  │  直方圖均衡化 + CLAHE 正規化                              │
  │      ↓                                                   │
  │  LBPH 特徵比對 predict()                                 │
  │      ↓                                                   │
  │  閾值判斷 + 連續 3 幀確認                                │
  │      ↓                                                   │
  │  標註框與名字                                            │
  │      ↓                                                   │
  │  寫入共用狀態（threading.Lock 保護）                     │
  └──────────────────────────┬───────────────────────────────┘
                             ↓
  ┌──────────────────── Flask 請求執行緒 ──────────────────┐
  │                                                          │
  │  GET /video_feed   → 取最新幀 → 編碼 JPEG → MJPEG 串流   │
  │  GET /api/status   → 回傳 FPS、臉孔、馬達狀態            │
  │  POST /api/motor/* → 馬達指令（MotorControl 加鎖）        │
  │  POST /api/train   → 背景執行緒重新訓練                    │
  └──────────────────────────────────────────────────────────┘
為什麼要拆成兩條線 如果把攝影機迴圈直接寫在 HTTP 請求處理裡，每個頁面請求都會重新開一次攝影機， 而且會阻塞其他請求。改成單一背景執行緒持續擷取、HTTP 只取「最新那一幀」， 即使辨識很慢，影像串流依然順暢。

模組分工

模組職責為什麼獨立出來
face_core.py 偵測、裁切、正規化、訓練、辨識 若三支腳本各寫一份，參數很容易不一致。而 LBPH 只要訓練與辨識的預處理有一點點不同，辨識率就會明顯下降
camera_source.py 統一鏡頭介面 電腦用 VideoCapture、車子用 Picamera2，上層程式無需分辨，是「先測後移」的關鍵
motor_control.py 馬達與雲台控制 唯一碰硬體的檔案。沒車時用模擬模式，上車改一個參數即可
03
演算法原理
ALGORITHM

HAAR Cascade — 人臉偵測

HAAR 的做法是：訓練時用大量「有人臉」和「沒人臉」的樣本，算出人臉區域在水平/垂直方向的明暗變化特徵， 推廣成一個小型決策樹。偵測時把影像逐層縮放，用滑動視窗逐一比對。

detector.detectMultiScale(
    gray,
    scaleFactor=1.1,   # 每次縮小的比例：越小越精確但越慢
    minNeighbors=5,    # 鄰居門檻：越大越嚴格、誤判越少
    minSize=(100, 100) # 最小人臉邊長：過濾遠距離雜訊
)

三個參數的取捨：scaleFactor 太小會大幅拖慢速度（實測 1.1 在 640×480 約 30 FPS）， minNeighbors 太低會把牆上的人像海報也當成臉。我們實測 1.1 / 5 是兼顧速度與準確度的設定；若移植到樹莓派，建議放寬到 1.3 / 3 提速。

LBPH — 人臉辨識

LBPH = Local Binary Patterns Histograms（局部二元模式直方圖），核心想法是把「紋理」量化成數字：

  1. 把人臉切成 8×8 = 64 個格子
  2. 每格取 3×3 鄰域，中心像素比鄰居大記 1、比鄰居小記 0
  3. 得到一個 0~255 的「紋理簽章」
  4. 64 個簽章各累加一個直方圖，合成 16384 維特徵向量
  5. 訓練時把所有向量存入模型；辨識時找最近的向量並回傳「距離」
參數我們的設定意義與取捨
radius1比較鄰居的半徑。調大能抓更粗的紋理，但特徵維度暴增、速度變慢
neighbors5鄰域取樣點數。調大更細緻但更慢
grid_x / grid_y8 / 8切幾格。格子越多特徵越精準，計算量也越大

距離與閾值

LBPH 的 predict() 會回傳「最近的訓練樣本」和一個 距離（越小越像）。 我們用閾值把結果分成三級：

距離範圍判定畫面顯示
≤ 60已註冊的人綠框 直接顯示姓名
60 ~ 85疑似同一人黃框 顯示姓名但標記為疑似
> 85陌生人橘框 顯示 Unknown

這些閾值是依據我們的實測數據訂定的（見第 07 節）。

影像正規化

LBPH 吃的是紋理，如果光線變化太大，紋理簽章就會整個改變而認不出人。 所以在裁切之後、餵進模型之前，先做兩道正規化：

  • 直方圖均衡化 — 把亮度值重新分布到整個 0~255 範圍，抵消整體明暗
  • CLAHE（限制對比度自适应直方图均衡）— 分區域處理，解決側光、局部過曝的問題
def normalize_face(gray_face):
    eq = cv2.equalizeHist(gray_face)          # 全域均衡化
    clahe = cv2.createCLAHE(clipLimit=2.0, tileGridSize=(8, 8))
    return clahe.apply(eq)                    # 局部均衡化
實測發現 我們最初以為正規化只是「加分」，實測後才發現它對弱光環境的辨識率影響非常大： 測試集中把照片亮度降到 0.65 倍，不做均衡化時距離明顯飆高，做了之後距離幾乎不變。 所以這兩行是必要的，不是裝飾。

05
疑難排解
TROUBLESHOOTING

以下是開發過程中實際遇到並解決的問題，依照「花時間最多的」排序。

ISSUE 01 訓練時照片被整批丟棄，60 張全部無法使用
症狀
執行 train_lbph.py 時，每張照片都顯示「偵測不到人臉，略過」，最後報錯「訓練失敗：所有照片都偵測不到人臉」。
原因
collect_faces.py 存檔時已經把臉裁切好了，但 train_lbph.py 又對這些「已裁切的臉」再跑一次 HAAR 偵測。 HAAR 需要足夠的周圍對比（頭髮、背景邊緣），對只剩五官的小圖根本偵測不到。
解決
訓練時直接使用照片的完整內容，不再二次偵測。照片既然是收集階段就已經裁切好的，再裁一次不但多餘，還會造成下面 ISSUE 02 的問題。
ISSUE 02 明明是同一人，卻被判定為陌生人
症狀
測試時同一位使用者，有時辨識成功（距離 19），有時卻顯示 Unknown（距離 86，超過閾值 85）。
原因
這是本次最關鍵的一個 bug。訓練輸入與辨識輸入不一致： HAAR 的框通常只涵蓋「眼睛到下巴」，對已裁切的人臉再裁一次會切掉臉部邊緣與額頭， 導致模型學到的紋理和實際辨識時送進去的紋理對不上，距離被灌大。
解決
確立一條原則：收集與辨識必須走完全相同的裁切流程。 收集時存 crop_face(HAAR框, padding=0.25)，辨識時用同樣的 crop_face(HAAR框, padding=0.25)，訓練時直接用存下的影像。 修正後同一情境的距離從 86 降到 19。
體會 這個問題在畫面上完全看不出來 —— 程式沒有 crash，訓練也「成功」了。 是靠逐項檢查距離數值才發現的。LBPH 這種「比對紋理」的演算法， 預處理的一致性比參數調得好壞更關鍵。
ISSUE 03 中文檔名存不下來，而且沒有任何錯誤訊息
症狀
用 python collect_faces.py 王小明 收集照片，程式顯示成功，但用檔案總管去看卻找不到任何檔案。
原因
cv2.imwrite() 在 Windows 上走的是 ANSI 路徑 API，遇到中文路徑會直接回傳 False， 不寫檔、也不丟例外。我們實測 cv2.imwrite("中文測試.jpg", img) 確實回傳 False。
解決
改用 imencode() 在記憶體中編碼，再用 numpy.tofile() 寫檔（走寬字元路徑 API）：
def imwrite_safe(path, image):
    path = Path(path)
    path.parent.mkdir(parents=True, exist_ok=True)
    ok, buf = cv2.imencode(path.suffix or ".jpg", image)
    if not ok:
        return False
    buf.tofile(str(path))      # numpy.tofile 支援寬字元路徑
    return True
實作後重新測試，30 張中文姓名照片全部寫入成功。
ISSUE 04 攝影機完全開不起來
症狀
cv2.VideoCapture(0) 回傳 False，換 DSHOW、MSMF 後端也一樣。
排查過程
依序檢查：裝置管理員有看到「ACER QHD User Facing」✓、攝影機沒被 Teams/Zoom 佔用 ✓、 Windows 隱私權設定允許 ✓。再用 pnputil /enum-devices /class Camera 確認裝置有註冊， 但 Get-PnpDevice 的 Status 顯示 Unknown，且 Win32_PnPEntity 完全查不到這台裝置。
原因
裝置被停用。pnputil /enable-device 回覆「需要重新啟動您的電腦」， 確認是驅動層的問題，不是程式問題。
解決
重新開機後攝影機立即恢復，實測 30 FPS 正常。結論：硬體問題要從驅動層查，不要在程式裡一直繞。
ISSUE 05 「連續 3 幀確認」機制完全失效
症狀
為避免辨識結果閃爍，我們設計了「連續 3 幀都認到同一人才顯示」的機制，但實測畫面依然會跳動。
原因
TrackState.update() 的 if 與 else 兩個分支都寫了 return self.current_label if self.hit_count >= CONFIRM_FRAMES else self.current_label， 三元的兩邊完全一樣，等於沒有判斷。
解決
改成兩階段設計：pending_label 暫存候選、pending_hits 累計次數， 只有連續達到 3 幀才把候選升級成 current_label。
if label == self.pending_label:
    self.pending_hits += 1
else:
    self.pending_label = label
    self.pending_hits = 1

if self.pending_hits >= CONFIRM_FRAMES:
    self.current_label = self.pending_label      # 正式確認
return self.current_label, score
另外發現追蹤的 key 原本用 bbox，但 bbox 會跟著呼吸晃動每幀都變， 當 key 等於永遠累積不到 3 幀。改成用「人臉中心的量化格子」（每 60px 一格）當 key。
ISSUE 06 Web 版線上註冊只存到 1 張照片
症狀
在網頁上輸入名稱、要求拍 30 張，結果 data/ 裡只有 1 個檔案。
原因
註冊 API 只在「開始註冊」時算一次檔名（tester01_001.jpg）， 之後每拍一張都覆寫同一個檔案，30 張全部寫進同一個檔名。
解決
改成依「目前已擷取數量」即時計算檔名：
n = task["count"] + 1
path = Path(task["dir"]) / f"{task['label']}_{n:03d}.jpg"
同時修掉另一個連帶問題：註冊完成時直接 state.register_task = None， 但區域變數可能已指向被新請求取代的舊 dict，會誤殺新任務。 改成先確認 state.register_task is task 才動作。
ISSUE 07 網頁上的「停止」按鈕完全沒反應
症狀
方向鍵都正常，但 STOP 按鈕點了沒反應，車子狀態一直停在上一個動作。
原因
事件綁定寫的是 $$('.dbtn').forEach(...)， 但 STOP 按鈕的 class 是 btn btn-stop，不是 dbtn， 所以它從來沒有被綁到事件。
解決
改用資料屬性綁定 $$('[data-action]')，與 class 完全脫鉤， 之後新增按鈕只要有 data-action 就自動生效。
ISSUE 08 雜項：中文亂碼與環境相容性
症狀
主控台中文顯示成亂碼；Flask 回傳的 JSON 中文變成 \uXXXX；OpenCV 錯誤訊息蓋掉自己的訊息。
原因與解決
  • 亂碼：Windows 主控台預設 Big5(cp950)，Python 輸出 UTF-8。呼叫 SetConsoleOutputCP(65001) 強制切 UTF-8。
  • Flask 3.x：app.config["JSON_AS_ASCII"] 設定已被移除， 改用 app.json.ensure_ascii = False。
  • OpenCV 5.0 API 變更：cv2.FaceRecognizerLBPH_create() 搬到 cv2.face.LBPHFaceRecognizer_create()。寫成相容兩版的 factory， 讓電腦（5.x）與樹莓派（4.x）都能跑同一份程式。
  • 錯誤訊息干擾：攝影機開不起來時 cv2 會噴 FFMPEG 錯誤。 設定 OPENCV_LOG_LEVEL=SILENT，並在 Windows 上移除 CAP_ANY（它會退回 FFMPEG 後端，該訊息會繞過 log level）。
  • 主控台沒進度：輸出重導向時 stdout 被緩衝，加 flush=True。
ISSUE 09 移植樹莓派後整個系統崩潰：module 'cv2' has no attribute 'data'
症狀
在 Raspberry Pi 上執行 self_test.py，HAAR 與完整流程兩項直接 FAIL，錯誤是 AttributeError: module 'cv2' has no attribute 'data'。程式在電腦上完全正常。
原因
原本程式用 cv2.data.haarcascades 找 HAAR cascade 檔案。 這個屬性是 Windows 的 opencv-python 套件才有的； Raspberry Pi 的 Debian OpenCV 是用 smbus/系統套件安裝的，沒有 cv2.data， cascade 檔案通常放在 /usr/share/opencv4/haarcascades/。
解決
新增 find_cascade_file()，依序搜尋四個來源，全部找不到就從 OpenCV 官方 GitHub 自動下載到專案內：
1. 專案內 cascades/          （自行管理，最可靠）
2. cv2.data.haarcascades      （Windows 專有）
3. /usr/share/opencv4/haarcascades  （Debian）
4. 自動從官方 GitHub 下載
實測在樹莓派上自動下載成功，self_test.py 從 2 項 FAIL 變成 17/17 全過。
ISSUE 10 馬達硬體設定全部猜錯，接上車子會往反方向跑
症狀
在寫 motor_control.py 時，我們是根據課程簡報的 PCA9685 規格推算通道對應的。 實際拿到課程提供的 LOBOROBOT2.py 後比對，發現每一項都錯。
原因
只看了簡報裡的「16 通道 PWM 控制器」說明，沒有車子的實際接線資訊就推估。
實際硬體
項目我們原本寫的（錯）LOBOROBOT2.py 實際值
馬達數量2 個4 個（左前/右前/左後/右後）
PWM 通道0, 10, 5, 6, 11
方向腳位未設定2/1、3/4、8/7；右後輪走 GPIO 25/24

關鍵細節
馬達 0 的方向極性是反的（not forward）， 代表它的接線和其他三顆相反。若照我們原本自行組 PWM 的寫法，車子會往反方向跑。
解決
放棄自行組 PWM，改為包裝 LOBOROBOT2.py， 所有動作都委派給它提供的方法（turnLeft()、movebackward() 等）。 這樣方向極性由課程檔案處理，不會搞錯。
體會 硬體相關的設定不能靠推理，一定要以實際檔案或實測為準。 這也正是我們一開始把 motor_control.py 和 camera_source.py 抽成獨立模組的原因 —— 把「會猜錯的部分」侷限在兩個檔案裡，出錯時改動範圍可控。
ISSUE 11 樹莓派 SSH 連不上，浪費大量時間排查
症狀
ping 樹莓派完全正常（3/3 回覆），但 ssh pi@10.207.166.4 永遠停在 kex_exchange_identification: Connection closed by remote host， 連密碼輸入畫面都沒出現。
排查過程
依序排除： 攝影機/網路卡 → 確認樹莓派在線（ping 通、ARP 有 MAC）→ 換 cmd / PowerShell / paramiko 三種客戶端 → 結果一致 → 換 Windows 行動熱點 → 正常。
原因
手機熱點開啟了 AP isolation（用戶隔離）， 讓同一熱點下的裝置互相看不到，ICMP 能通但 TCP 22 的完整握手被中間設備切斷。
解決
改用 Windows 行動熱點（Windows 預設不開 AP isolation）。 之後 SSH 一次就通，順利完成整個部署。
診斷技巧 「ping 通但 TCP 握手失敗」這個組合幾乎可以直接判定是 AP isolation 或中間防火牆， 而不是目標主機本身的問題。換一個網路環境測試是最快的確認方式。

def identify_faces(gray, detector, recognizer, labels):
    """在整張灰階影像上偵測 + 辨識所有人臉"""
    results = []
    for (x, y, w, h) in detect_faces(gray, detector):
        roi = normalize_face(
            cv2.resize(crop_face(gray, (x, y, w, h)), (200, 200)))

        pred_id, distance = recognizer.predict(roi)
        distance = float(distance)

        if distance <= THRESHOLD_WEAK and 0 <= int(pred_id) < len(labels):
            name = labels[int(pred_id)]
        else:
            name = "Unknown"

        results.append({
            "rect": (x, y, w, h),
            "name": name,
            "distance": distance,
            "is_known": name != "Unknown",
        })
    return results

馬達控制的模擬 / 真實雙模式

class MotorControl:
    def __init__(self, mode=MODE_SIMULATION):
        self.mode = mode
        self.lock = threading.Lock()      # 保護 I2C，避免多執行緒衝突

    def move(self, action, speed=None):
        with self.lock:
            if self.mode == MODE_SIMULATION:
                self._simulate(action, speed)
            else:
                self._drive(action, speed)
            return self.state.to_dict()

    def _drive(self, action, speed):
        """真實模式：驅動 PCA9685（課程 I2C / PWM 內容）"""
        base, half = speed, speed // 2
        left, right = self._wheel_targets(action, base, half)

        # 後退緩啟動：避免 RPi 5 瞬時電流尖峰
        if action.startswith("backward") and self.soft_start_delay > 0:
            time.sleep(self.soft_start_delay)

        self._set_channel(self.CH_LEFT,  abs(left)  / 100.0)
        self._set_channel(self.CH_RIGHT, abs(right) / 100.0)
對應課程內容 _set_channel() 實作的正是課程簡報的 PCA9685 暫存器操作： LEDx_ON_L = 0x06 + 4x、LEDx_OFF_L = 0x08 + 4x， PRESCALE = 25000000 / (4096 × 50 - 1) ≈ 121。 目前因為還不能領車而以模擬模式驗證，上車時改 mode=MODE_RPI 即可。

REFLECTION

心得

這次作業最大的收穫不是「學會了 HAAR 和 LBPH」， 而是體會到影像處理的環節順序會決定成敗。

我們在 ISSUE 02 卡了最久。程式沒有 crash、訓練沒有報錯、畫面也正常顯示框， 看起來一切正常，但同一個人就是不斷被判定成陌生人。 最後是因為我們很仔細地把每個測試案例的距離數值列出來對照， 才注意到「同一個測試條件，距離居然從 19 跳到 86」。 追下去才發現是訓練與辨識的預處理不一致。

這讓我們體會到：AI 影像處理最容易出現的不是「明顯的錯誤」， 而是「看起來正常但結果微妙地錯」的問題。這種問題靠讀程式碼很難發現， 必須要設計出能揭露差異的測試。之後我們把 self_test.py 寫得很細， 就是希望後續修改時能立刻抓到這類回歸。

第二個收穫是硬體相依要隔離。現在還不能領車，但我們把鏡頭和馬達 分別抽象成 camera_source.py 和 motor_control.py， 用模擬模式就能把整個 Web 介面、多執行緒、API 全部測完。 等車子到手，只要改一個參數就能接上真實硬體， 不用再重寫一輪。雖然多花了時間寫抽象層，但省下的是之後重測的時間。

建議

📸
採集照片要多變化
不要只拍同一個距離和角度。我們實測發現人臉佔畫面比例改變時， 距離會從 19 跳到 53。遠中近三種尺度都要收，辨識率會好很多。
🎯
用數值驗證而非只看畫面
把 LBPH 距離輸出成數值，建立測試案例對照表。 只看「有沒有框出來」會完全看不出預處理不一致的問題。
🔒
執行緒安全要從一開始就做
Flask 是多執行緒環境，共用狀態全部加 threading.Lock。 課堂提到的 I2C 當機就是這個原因，現在先做好上車就不用重調。
🧱
硬體相依集中管理
把所有碰 I2C / 攝影機的程式碼集中在一兩個檔案， 沒硬體時也能完整測試，上車時改動最小。
